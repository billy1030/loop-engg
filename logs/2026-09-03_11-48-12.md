| **Downtime 感受** | **真正零停機**（95% 背景同步，最終切換 5–10 分鐘） | 必須公告**維護窗口**（通常 1–2 個週末） |
| **郵件遺失風險** | 趨近於零（MRS 增量同步每 24 小時，最終切換走 targetAddress） | **較高**——切換窗口期內若 DNS MX 未正確切換會丟信 |
| **回滾能力 (Rollback)** | ✅ **可雙向搬遷**（這是唯一原生支援的雙向方法） | ❌ 無回滾機制 |
| **共存期功能** | ✅ 共用 GAL、跨環境 Free/Busy、MailTips、跨信箱搜尋、OAuth | ❌ 無；切完即拆夥 |
| **目錄同步 (Entra Connect)** | ✅ 必要，且須常駐 | ❌ 禁用（會導致遷移失敗） |
| **Modern Authentication / OAuth** | ✅ 完整支援 | ❌ 不適用 |
| **批次控制粒度** | 可任意分批（如 50–100 人/批） | 一次性整批 |
| **複雜度** | 高（需 HCW、Entra Connect、憑證、Firewall） | 低 |
| **適用情境** | 中大型企業、重視零停機/合規/共存 | ≤150 人的微型組織、無法執行 Entra Connect |
| **2026 年支援狀態** | ✅ 主流路徑（推薦 Modern Hybrid Topology） | ⚠️ 仍可用但已非戰略方向 |

### 為什麼 Cutover 不適合您的 500 人場景？

微軟在多份官方文件中**反覆強調**：「如果您要遷移的信箱數超過 150，**請使用 Exchange 混合遷移**，因為在嘗試遷移 150 個以上信箱時，cutover 效能會大幅下降」（節錄自 learn.microsoft.com/en-us/exchange/mailbox-migration/decide-on-a-migration-path）。

直接切換對您的兩個硬性指標都有致命傷：
- ❌ **用戶必須重建 Outlook profile** → 違反「用戶無感過渡」
- ❌ **沒有原生回滾** → 「零邮件丢失」無法保證
- ❌ **不支援 OAuth 現代驗證** → 2026 年 3 月起 Basic Auth 關閉後即報廢

## 三、✅ 架構建議：採用 **Full Hybrid Migration + Modern Hybrid Topology**

基於您的硬性指標（零丢失 + 用戶無感），**唯一符合的方案是混合遷移**。進一步建議採用 **Modern Hybrid Topology**（Hybrid Agent v2），這是微軟在 2026 年明確推薦的下一代架構。

### 3.1 為何選 Modern Hybrid Topology（而非 Classic）

| 項目 | Classic Hybrid | **Modern Hybrid (Hybrid Agent)** |
|---|---|---|
| 對外開放 Inbound Port 443 | 需要 | **不需要**（大幅降低資安曝險） |
| 對外 EWS / Autodiscover DNS | 需公開 | **不需要** |
| 公網 SSL 憑證 | EWS 必須 | **SMTP 仍需，但 EWS 不用** |
| 通訊方向 | 雙向 | **純 outbound**（走 Entra Application Proxy） |
| Free/Busy 跨環境查詢 | ✅ | ✅ |
| MRS 信箱遷移 | ✅ | ✅ |
| 訊息追蹤 / 多信箱跨環境搜尋 | ✅ | ❌（限制） |
| Hybrid Modern Auth (OAuth) | ✅ | ❌（限制） |
| Teams 行事曆整合 | ✅ | ❌（限制） |

**建議決策**：
- 若您**無需**訊息追蹤跨環境查詢、不在意 Hybrid Modern Auth 的 OAuth 進階體驗、且想**大幅降低對外曝險面** → 選 **Modern**。
- 若您是金融/合規產業、必須保留 Teams 行事曆與跨環境 eDiscovery → 選 **Classic**。

> 對於一般企業 500 人，**建議採 Modern Hybrid**，這也是 2026 年的微軟主推方向。

## 四、🛡️ 達到「零郵件丟失」與「用戶無感」的關鍵機制

### 4.1 零停機的核心：MRS 增量同步 + 手動完成模式

依據 Microsoft 官方 Q&A 的權威說明，hybrid 遷移的運作流程：

1. **背景同步 95% 資料**——使用者繼續在本地信箱工作，無感
2. **增量同步每 24 小時執行一次**——把過去 24 小時的新郵件同步上雲
3. **最終切換 (Completion) 鎖定本地信箱 5–10 分鐘**——處理最後 5% 的差異同步
4. **Outlook 自動重連**——信箱 GUID 不變、profile 不變，僅 Outlook 短暫斷線（OWA 仍可訪問）
5. **切換後**：本地信箱變為 `Remote Mailbox (mail-enabled user)`，targetAddress 自動指向雲端——所有新郵件從雲端遞送

### 4.2 零郵件丟失的保證

- ✅ **Secure Mail Flow** 連接器：本地 → 雲、雲 → 本地的雙向 TLS 通道
- ✅ **跨環境 targetAddress**：本地信箱與雲信箱維持 x500 / targetAddress 雙向路由
- ✅ **30 天寬限期**：即使雲端信箱尚未指派授權，Microsoft 允許 30 天內補上（無資料被刪）
- ✅ **MX 預降 TTL**：切換前 48 小時將 MX TTL 從預設 3600/14400 降至 **300 秒**，避免切換後郵件走錯路

## 五、⚠️ 必要的前置條件清單（500 人場景務必逐項確認）

### 5.1 Exchange Server 端
- [ ] Exchange 2016 **CU13 或更新**（CU23 強烈建議）
- [ ] **MAPI over HTTP 已啟用**
- [ ] **.NET Framework 4.8** 已安裝
- [ ] **TLS 1.2** 強制啟用（Basic Auth 關閉後必要）
- [ ] **公網 CA 簽發的 SSL 憑證**（覆蓋 Autodiscover 與 mail flow 命名空間）— 自簽憑證**不被支援**
- [ ] **MRSProxy** 在 EWS 虛擬目錄啟用：`Set-WebServicesVirtualDirectory -Identity "EWS (Default Web Site)" -MRSProxyEnabled $true`
- [ ] **Autodiscover DNS** 公開指向本地 Exchange（Classic 模式必要）

### 5.2 Microsoft 365 端
- [ ] 已驗證的自訂網域
- [ ] 已指派授權（Microsoft 365 Business Premium 或 E3/E5）
- [ ] 全域管理員帳號
- [ ] Exchange Online 為**接受網域狀態**

### 5.3 目錄同步
- [ ] **Entra Connect** 安裝並勾選 **Exchange Hybrid Deployment**
- [ ] 內部 AD 的 UPN 與電子郵件網域一致（避免 `company.local` 問題）
- [ ] 執行 **IdFix** 修復重複屬性、無效字元
- [ ] 移除離職帳號、清理 proxyAddresses 重複

### 5.4 網路
- [ ] **Outbound TCP 443** 至 Microsoft 365 端點（Modern Hybrid 唯一需求）
- [ ] **Outbound TCP 25** 至 Exchange Online（郵件流仍走 SMTP）
- [ ] 帶寬估算：建議**信箱總量的 1.5 倍**
- [ ] 使用 **Microsoft Remote Connectivity Analyzer** 預先驗證

## 六、🔄 風險緩解與回滾計畫

| 風險 | 緩解措施 |
|---|---|
| 遷移中途失敗 | Hybrid 支援**雙向搬遷**，可用 `New-MoveRequest -RemoteTargetDatabase` 把雲端信箱搬回本地 |
| 切換後使用者發現問題 | 保留本地 Exchange 30 天；使用者登入 Outlook 時若指向本地，自動走本地信箱 |
| DNS MX 切換延遲 | 切換前 48 小時降低 MX TTL 至 300 秒 |
| 大信箱 (>50 GB) 逾時 | 啟用自動擴展封存、預先歸檔歷史郵件、分批於離峰時段處理 |
| Modern Auth 準備不足 | 提前完成 OAuth 設定，2026 年 3 月後將強制要求 |
| Hybrid Agent 單點故障 | Modern 模式下建議部署**多台** CAS 並輪詢，避免單一節點離線導致 free/busy 中斷 |
