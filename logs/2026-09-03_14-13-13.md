# F5 Monitor Showing "Reject/Reset" in 1 Second — Troubleshooting Hints

Since ping works and they're on the same subnet, **L3 connectivity is fine**. The fast 1-second reject/reset tells you the probe is reaching the server but being actively refused (not a timeout). Here are the most likely culprits in order:

---

## 🎯 Top Suspects (90% of cases)

### 1. **Server-side firewall blocking the F5's self-IP** ⭐ Most Common
The server's local firewall (Windows Firewall, `iptables`, security group, host-based IDS) is blocking the monitor's source IP — even though it allows ICMP (ping).

**Check:**
- On the server: `iptables -L -n -v` (Linux) or `Get-NetFirewallRule` (Windows)
- Look for DROP/REJECT rules on the pool member port
- Add an allow rule for the F5's **self-IP** (not the VIP) on the relevant VLAN

### 2. **No service listening on that port**
The OS responds with TCP RST because nothing is bound to the monitor's destination port.

**Check from F5 CLI:**
```bash
# Test the actual probe port directly
curl -vk http://<node-ip>:<port>/   # for HTTP monitors
telnet <node-ip> <port>             # for TCP monitors
nc -zv <node-ip> <port>             # quick port check
```

### 3. **Wrong port in the pool member / monitor**
Pool member port ≠ the service port (e.g., app listens on 8080 but monitor checks 80).

---

## 🔧 Quick Diagnostic Steps

### Step 1: Enable monitor logging (do this first!)
- GUI: **Local Traffic → Nodes → [node] → Health Monitors → Enable "Monitor Logging"**
- Or via tmsh:
  ```bash
  tmsh modify ltm node <node-ip> monitor-logging enabled
  ```
- Then check `/var/log/ltm` for detailed failure reason — it will tell you exactly why.

### Step 2: Packet capture on the F5
```bash
tcpdump -ni 0.0:nnn -s0 host <node-ip> -w /var/tmp/monitor.pcap
```
Look for: SYN going out → **RST/ACK or ICMP unreachable coming back**. That confirms the server (or an inline firewall) is actively rejecting.

### Step 3: Verify which self-IP F5 is sourcing from
```bash
tmsh list /net self | grep -i <vlan>
```
Make sure the self-IP on the server-side VLAN is the one the server expects. If using **SNAT / Automap**, the F5 might be sourcing from the wrong interface (e.g., a floating self-IP on the wrong VLAN).

### Step 4: Check interval vs. timeout
F5 recommendation: **timeout = (3 × interval) + 1**
- Default is `5/16` (5s interval, 16s timeout)
- 1s response = NOT a timeout issue, but worth confirming anyway.

---

## 🚨 Other Things to Rule Out

| Check | Why |
|---|---|
| **Port-locked / iRule on VIP** | iRules can interfere with monitor source IPs |
| **Big-IP packet filter (port 54321)** | Known bug — internal firewall can send ICMP unreachable to monitor probes (fixed in 12.0.0) |
| **In-TMM monitoring bug** | `bigd.tmm = enable` can mark members down erroneously on delayed pings |
| **Alias address vs. service port** | Node has alias `*:5061` but service isn't on that IP |
| **Different VLAN / routing** | Even "same subnet" — confirm both F5 self-IP and node IP are in the same broadcast domain on the same VLAN |
| **ARP/IP conflict** | Duplicate IP on the segment causing RSTs from the wrong host |

2. If SYN/RST → fix the **server** (firewall or start the service on that port)
3. If no reply at all → fix the **path** (firewall, VLAN, or self-IP)
4. Enable **monitor logging** to get the exact reason string in `/var/log/ltm`
